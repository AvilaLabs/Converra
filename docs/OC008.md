# OC-008: bracketing refinement of the OC-007 cost optimum

Run September 10, 2026. OC-007 found the cheapest of 15 hand-declared `(turns, tapes)` geometries: 120 turns x 4 tapes at $41,513.13. Under this model, at a fixed pancake count `p` (tapes along width), utilization rises and cost falls as the turn count `n` falls, so the cheapest passing design at that `p` is the smallest passing `n`. OC-008 finds `n*(p)` by bracketing bisection, to a declared resolution, for each `p` in a declared set — extending OC-007's own `{2, 3, 4}` tapes with two previously unsampled counts, `5` and `6` — then selects the cheapest across `p`, screened and accepted through the identical OC-004 coupled runner and OC-007 acceptance module. As with OC-007, every dollar figure is a **modeled saving under synthetic prices and a screening model**, never a production claim.

## Run and reproduce

```bash
# Frozen case, full record to a file and to stdout.
cargo run --release --offline -- coupled-refine benchmarks/coupled/oc-008.json \
  --threads 5 --output runs/oc-008-<date>.json --json

# Embedded case via the dedicated subcommand (equivalent to the command above).
cargo run --release --offline -- coupled-refine-benchmark --threads 5 --json
```

`coupled-refine`/`coupled-refine-benchmark` exit 0 only when `search_status` is `PASS` **and** the embedded `acceptance.agreement_status` is also `PASS`; otherwise the process exits nonzero while still writing/printing the full JSON record. `--threads` may only lower the case's own declared `execution.max_threads` (5). Files are never overwritten. The frozen run below (2,756.3 s) was produced under a session-local memory-containment wrapper (a `systemd-run` cgroup memory cap, three build jobs, one cargo invocation at a time) needed because this laptop has 30 GB of RAM and a prior out-of-memory event during an unrelated full-workspace build; that wrapper is a session tool for this development environment, not part of this repository, and a plain `cargo run --release` invocation reproduces the same computation on a machine with sufficient free memory.

Each declared bracket must itself be verified before any bisection proceeds for that pancake count — see below.

## Bisection and bracket rule (per pancake count, contract §2 B3)

1. Evaluate both bracket ends through the OC-007 candidate pipeline (requirement -> NI -> I_op -> coarse pruning -> full plan).
2. The bracket is valid only if `fail_turns` FAILs (or is INCONCLUSIVE) and `pass_turns` PASSes; otherwise `bracket_status: INVALID` is recorded, nothing further is evaluated for that `p`, and it is excluded from the global optimum.
3. Bisect on integer `n` until `pass - fail <= turn_resolution` (2 turns here); `n*(p)` = the smallest evaluated `n` that PASSes.
4. Monotonicity check: utilization must be nonincreasing in `n` across every evaluated `n` for that `p`; a violation makes that `p`'s result `INCONCLUSIVE` (the bisection assumption failed).
5. Every evaluated candidate is recorded exactly as OC-007 records a candidate (coarse pruning, full plan, cost, screening).

Global optimum = the cheapest `n*(p)` with a valid, monotone bracket, ties by fewer total turns. All five brackets here came back `bracket_status: VALID` with `monotonicity_ok: true` (`checks[0]`: *"5 of 5 pancake counts bisected (5 PASS, 0 INCONCLUSIVE (monotonicity violation), 0 INVALID bracket)"*), so none were excluded.

## Required interpretation

**(a) The optimum sits at the top of the declared pancake range.** `n*(p)` fell monotonically as `p` rose from 2 to 6 (258, 168, 120, 90, 72 turns; $43,032, $42,759, $41,513, $39,781, $39,022), and `p = 6` is the largest pancake count this case declared. This case did not test `p = 7` or higher, so under this model the true (per-this-screening-model) optimum likely lies at a higher pancake count still — until per-pancake assembly ($500) and joint ($200) costs, which grow linearly with `p`, come to dominate the falling conductor length. This was not explored by design and is stated here as a limitation, not hidden: **OC-008 does not establish that `p = 6` is a global optimum over all pancake counts, only over the declared set `{2, 3, 4, 5, 6}`.**

**(b) Every `n*(p)` sits within 0.5-2.4% of the utilization limit by construction.** The bisection's entire purpose is to find the smallest passing `n`, i.e. the design closest to the 0.8 utilization ceiling from below, for each `p` (utilizations 0.7998, 0.7965, 0.7900, 0.7884, 0.7765 — all within 0.0235-0.0348 of 0.8). These designs therefore carry **no margin beyond the two modeling knobs already in the case**: the declared 10% `interpolation_overprediction_budget` and the 0.8 `utilization_limit`. This is not a demonstrated engineering margin.

**(c) Everything here is a modeled saving under synthetic prices and a screening model.** The cost model is an invented placeholder ($30/m conductor, 10% scrap, $500/pancake assembly, $200/joint interface), not supplier data. The physical gate is the OC-004 coupled screening margin under its declared assumptions (homogenized pack, applied-field-as-local-field, period-180/mirror-pair angle policy, no self-field redistribution). `conductor_qualification_status` is `INCONCLUSIVE` and `engineering_status` is `NOT_EVALUATED`, unchanged from OC-004/OC-007. The OC-005/OC-006 multi-axis interpolation caveat (three-axis stratum worst positive error 8.637%, retaining but not proving the 10% overprediction budget; whole-fold status `FAIL` on a separate, conservative-direction gate) and the width-transfer gap (`width_transfer.basis: none`) carry over unchanged.

## What this does not establish

- **Synthetic prices**, exactly as OC-007: every dollar figure is an invented placeholder cost model, not supplier data or a production cost estimate.
- **Screening model**, exactly as OC-004/OC-007: the physical gate is the OC-004 coupled screening margin under its declared assumptions, never a qualified operating current.
- **Not a global optimum over pancake count.** As stated under "Required interpretation" above: `n*(p)` fell monotonically through the entire declared range `p in {2, ..., 6}`, so a higher pancake count was never tested and may cost less still, until assembly/joint costs (which scale with `p`) dominate. This is the single largest open question this record leaves unanswered.
- **No remaining margin beyond the declared limits.** Every `n*(p)`, by the bisection's own construction, sits within a couple of percent of the 0.8 utilization limit; the design carries no headroom beyond the 10% interpolation-overprediction budget and the 0.8 utilization limit already declared in OC-004.
- **Bisection resolution.** `n*(p)` is only located to within `turn_resolution = 2` turns; the true continuous-turn-count optimum at each `p` was not searched.
- **No per-candidate independent reference**, exactly as OC-007: every candidate's `numerical_status` is `INCONCLUSIVE` by construction; `refinement_status` PASS and the acceptance module's refined-plan re-check are the checks this record relies on instead.
- **No width transfer.** `width_transfer.basis` is `none`, unchanged from OC-004/OC-007: no Jc nonuniformity across the tape width or batch variation is modeled.
- **One specimen.** All conductor data traces to the same single research specimen OC-003 through OC-008 already used.
- **The OC-005/OC-006 multi-axis interpolation limitation carries over unchanged.** The three-axis stratum's worst 25.03% error is an underprediction that can inflate material requirements and weaken modeled savings; the 8.64% worst overprediction supports the retained 0.10 `interpolation_overprediction_budget` but does not prove a bound on it.
- **No mechanics, thermal or quench.** None of these are modeled, unchanged from OC-004/OC-007.
- **Conductor qualification INCONCLUSIVE; engineering NOT_EVALUATED.** As declared throughout OC-004/OC-007 and unchanged here.
