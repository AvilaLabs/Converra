# OC-011: Bluemira kernel cross-check — independent magnetostatics evidence

Status: **Phase A and Phase B implemented and live-verified.** Phase B
results below; the original Phase A record follows. Written after the
OC-010 real-coil benchmark (Feather-M2 spec) showed the optimizer
tracking a built coil's conductor mass to ~3% — which raised the stakes
on the kernel: every search and acceptance verdict rests on our own
`RacetrackEvaluator`. One implementation producing self-consistent
answers is necessary but not sufficient; the claim hardens when a second,
independently developed implementation agrees on the same frozen inputs.

Live results (Bluemira `2.15.1.dev6+ga17002aeb`, installed from git —
it is not on PyPI or conda-forge; CAD/FEM deps stubbed in the dev venv,
never exercised by the filament path):

- Loop deck (L=0) vs in-tree closed form: Bluemira 2.09446 T vs analytic
  2.09440 T at 100 kAt on R=0.03 — plumbing and conventions verified.
- OC-010 parity cell (80x4 pack, L=0.10, R=0.028): **PASS**, max
  |dB|/B = 5.4e-4 over 28 probes, max direction delta 0.012 deg.
- Two further optimum cells (L=0.125/R=0.028, L=0.10/R=0.034): PASS at
  3.9e-4 and 5.4e-4. Records in `runs/oc010-featherm2/crosscheck-*.json`.
- Residuals sit at the polygonal-discretization scale (512 arc segments
  our side vs 256 in the runner), exactly where Phase A should land.

[Bluemira](https://github.com/Fusion-Power-Plant-Framework/bluemira) is
an open-source fusion power-plant framework (UKAEA/EUROfusion lineage)
whose magnetics library includes thin-filament Biot–Savart, semi-analytic
finite-cross-section sources, circular-arc sources, and a
`PolyhedralPrismCurrentSource` for arbitrary polygonal cross sections —
an independent implementation of exactly the math our kernel does.

## The narrow question

Do NOT ask Bluemira whether a design is good, or to optimize anything.
Ask only:

> For this exact racetrack geometry, current, coordinate convention, and
> frozen probe list — what is (Bx, By, Bz)?

Then compare against `RacetrackEvaluator::evaluate` at the same probes
under a predeclared tolerance. Agreement upgrades the kernel claim from
"self-consistent" to "independently confirmed"; disagreement is a found
bug either way.

## Request contract (why not `SolverRequest`)

`optcoil-adapters::SolverRequest` carries `(Case, Candidate)` — the
OC-001-era single-coil model — and `SolverAdapter::evaluate` answers
"does this candidate pass". The cross-check asks a different question:
"does this *kernel* agree". Shoehorning a probe deck into a Candidate
corrupts both contracts. Therefore:

- `optcoil-adapters` gains `KernelProbeRequest`: a serializable deck of
  `{geometry: {straight_half_length_m, bend_radius_m, radial_width_m,
  axial_height_m, tape_normal, operating_current_a}, probes_m: [[x,y,z]...]}`.
- A `KernelCrosscheck` trait sits beside `SolverAdapter`:
  `evaluate_deck(&KernelProbeRequest) -> Result<KernelEvidence, AdapterError>`.
- `KernelEvidence` = per-probe `{b_t: [f64;3]}` plus `solver_name`,
  `solver_version`, `request_sha256`, `response_sha256` — the same
  evidence shape as `SolverEvidence`, so Core binding is free later.

## Geometry mapping

Our racetrack: two finite-cross-section straights (along x, at |y| =
R·something — the pack band) joined by two semicircular bends centered
at (±l, 0), tape normal radial. Map to Bluemira as:

1. **Phase A — thin-filament**: the centerline path (2 straights + 2
   semicircle arcs) carrying the pack's full NI. Implemented:
   `optcoil-physics::filament` evaluates our side (analytic
   finite-segment Biot–Savart, 512 chords/arc — *not* a shrunken
   cross-section, which the cell budget correctly forbids), and
   `tools/bluemira_probes.py` feeds the same closed polygon to
   `BiotSavartFilament`.
2. **Phase B — finite cross-section** (the model search verdicts
   actually run on): `ArbitraryPlanarPolyhedralXSCircuit` sweeps the
   real rectangular pack cross-section along the same centerline
   polygon as mitered `PolyhedralPrismCurrentSource` segments
   (Fabbri's analytic surface-integral kernel — a genuinely different
   method from our volume quadrature, on the same uniform-J physical
   model). **Implemented and live-verified.**

## Phase B live results

Same venv and Bluemira build as Phase A. Decks declare
`evaluation_model: "finite_cross_section"` (a v1 deck field that
existed for exactly this); our side routes to `RacetrackEvaluator`
at the real pack XSC, the runner builds the swept-prism circuit with
uniform current density NI/(w·h) — the same physical model, different
mathematics.

- Loop deck (L=0, R=0.03, w=h=0.01, 100 kAt): PASS, rel ~4e-6. The
  finite-XSC center field (2.0840 T) sits *below* the centerline
  filament (2.0944 T): axial spread costs more than the 1/r radial
  weighting gains at this aspect ratio — the ~1% difference Phase B
  exists to check.
- OC-010 optimum cells (80x4 pack, real Feather-M2 geometry), 28 probes
  each (bore + region lattice):
  - L=0.100 R=0.028: **PASS**, max |dB|/B = 2.8e-6, dir 0.000 deg
  - L=0.125 R=0.028: **PASS**, max |dB|/B = 2.2e-6, dir 0.000 deg
  - L=0.100 R=0.034: **PASS**, max |dB|/B = 4.1e-6, dir 0.000 deg
  - Records: `runs/oc010-featherm2/crosscheck-fxsc-*.json`.

The ~ppm agreement is expected once discretization is shared: Phase A
compared two *different* polygonal filaments (512 vs 256 chords, hence
5e-4); Phase B compares analytic prisms vs high-order quadrature on the
same continuous pack, leaving only quadrature and miter residuals.

Runner notes: the swept circuit needs the loop already closed —
`centerline_nodes` ends exactly at its first point, so the runner snaps
the last node onto it rather than appending a duplicate (a repeated
node is a zero-length prism segment whose field is NaN). The
`unequal end cap` warning from Bluemira's miter heuristic is benign
here — all vertex half-angles are equal and small.

CLI: `optcoil crosscheck --record run.json --evaluation-model
finite_cross_section` (thin_filament remains the default).

Probes: the region lattice (the requirement's own 27 points) plus a few
mid-gap/edge probes. The deck is canonical JSON — floats as decimal
strings — so its sha256 is stable across implementations and languages.

## Tolerance and verdict

- Gate (declare before first run; adjust only with a documented reason):
  `|B_bluemira - B_rust| / |B_rust| <= 1e-3` on the field magnitude per
  probe, with an absolute floor of `1e-4 T` for near-zero components;
  field direction agreement within 0.5 degrees.
- Verdict semantics stay ours: PASS (within tolerance at every probe),
  FAIL (any probe exceeds), INCONCLUSIVE (degenerate |B| too small to
  compare, i.e. below the floor at every probe — treated as "no signal
  to check"), and a Bluemira-absent environment yields NOT_EVALUATED —
  never silently skipped.
- The result is a `Check` in the run record (`kernel_crosscheck`), so an
  acceptance pass can later require it; initially it runs on demand.

## Wiring

- `tools/bluemira_probes.py` — standalone runner (same subprocess shape
  as the Core pilot's Python runners): reads the deck, builds the
  source, writes canonical `{b_t}` answers + `bluemira.__version__`.
- Rust: `BluemiraCrosscheck` in `optcoil-adapters` — spawns the runner,
  hashes request/response, builds the comparison checks.
- Exercise path: `optcoil crosscheck --deck deck.json` (or
  `--case` → deck extracted from a coupled-search case's best
  candidate), printing the verdict JSON. Long-running? No — seconds.

## Prerequisites and risks

- `pip install bluemira` — heavy (OpenCASCADE, numba, …). It is an
  *optional* dev-side dependency only: nothing in the crate or the
  search path links it. Record `solver_version` in evidence; pin the
  tested version in this doc once known.
- Coordinate/convention mismatch is the expected first bug — the deck
  must state axes and units explicitly; verify first against the closed
  form we already have (`circular_loop_axis_bz_t` on a loop deck) before
  trusting the racetrack comparison.
- Numerical precision: our evaluator uses fixed-order quadrature over
  cells; Bluemira's filament is a different discretization — agreement
  to ~1e-3 is expected, not exactness. If it lands at 1e-6 that's the
  quadrature being the shared error; still a pass.

## Out of scope (explicit)

- Bluemira's own optimizers (SLSQP/COBYLA/…/DIRECT) and geometry
  parameterizations (PrincetonD, TripleArc, PictureFrame): candidate for
  a later bilevel general-shape study — our (L,R) outer loop already
  plays that role for racetracks.
- Bluemira's 3-D beam mechanics solver: candidate for a later
  `mechanical_preliminary_screen` verdict — explicitly not
  engineering acceptance; screens only.
- Neither is a substitute for the Allsolve/COMSOL/Ansys connectors;
  Bluemira answers the *independence* question, not the *fidelity* one.
